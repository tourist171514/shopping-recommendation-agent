# 01 需求分析：购物 Agent 原型系统（Web 版）

> 依据：`任务1_Agent工作流构建_题目.md` + 材料包数据实际勘察结果
> 模型：DeepSeek V4 Pro（API，OpenAI 兼容接口）
> 拓展方向（选定）：多轮对话、主动追问

---

## 1. 背景与数据勘察结论

题目要求构建一个购物 Agent：理解自然语言购物需求 → 检索商品 → 比较候选 → 检查约束 → 做出购买决策 → 说明结果。交互形式自定，本项目采用 **Web 页面**。

对 `data/` 的实际勘察得出三个直接影响设计的结论：

| 勘察发现 | 设计影响 |
|---|---|
| 商品仅 96 条、2 个品类（shirt/mug），22 个制造商、102 个标签 | 检索用**结构化过滤 + 关键词匹配**即可，无需向量库 |
| `description` 字段全部为拉丁占位文本，无语义 | 语义检索只作用于 `name + tags`，不作用于 description |
| 50 条任务分为 3 种句式，其中 "prefer X if available"/"affordable" 属于**软偏好** | 约束体系必须区分**硬约束**（不满足即淘汰）与**软偏好**（只加分不淘汰） |

## 2. 功能需求

### 主干功能（题目必做）

| 编号 | 功能 | 说明 | 实现层 |
|---|---|---|---|
| F1 | 需求理解 | 自然语言 → 结构化约束 `{item_type, tags, manufacturer, max_price, soft_prefs}`，区分硬/软 | LLM（1 次调用，JSON 输出） |
| F2 | 商品搜索 | 一级：结构化过滤（类型+价格）；二级：标签/名称/厂商匹配打分，返回 Top-K 及匹配明细 | 纯代码，**0 token** |
| F3 | 候选比较 | 仅 Top-K（K≤5）进入 LLM 上下文比较，输出排序理由 | LLM |
| F4 | 约束检查 | 硬约束逐条校验（通过/违反+证据）；软偏好计分；候选为空时给出"差在哪"的诊断 | 代码校验 + LLM 诊断 |
| F5 | 购买决策 | 选出唯一最优 → `purchased_product_id`；无合格候选 → `None` | 代码（基于 F3/F4 分数） |
| F6 | 结果说明 | 自然语言解释：为什么选它/为什么没选，每个约束的作用 | LLM（与 F3 合并为一次调用） |

### 拓展功能（选定深做）

**F7 多轮对话**
- 会话管理：每个会话有 `conversation_id`，服务端保存对话历史与**累积约束状态**
- 增量更新：新一轮输入只更新提到的约束，未提及的保留（如第一轮定了"shirt + Ocean 主题"，第二轮只说"预算 15 以内"）
- 支持中途改条件与反悔："太贵了换个便宜的"、"不要这个厂商了"、"第二个看看"

**F8 主动追问**（触发条件三选一）
1. **信息不足**：类型/主题/预算缺失过多，无法形成有效检索 → 追问缺失项
2. **零结果**：检索无候选 → 说明哪个约束过严，给出可点击的放宽选项（提价/换厂商/换主题）
3. **表述模糊**："affordable" 等模糊词 → 确认预算区间

追问策略（关键设计决策）：
- 有候选但信息不全 → **给出当前条件下的推荐 + 顺带追问**（不让用户空手等）
- 零候选 → **必须追问**，并给出放宽方案让用户选择

### 兼容需求（对接官方评测骨架）

- 保留 `Agent(data_dir).run(instruction)` 单轮接口约定，`starter/simulate_agent.py` 无需修改即可批量回归 50 条任务
- Web 后端调用同一个 Agent 核心，保证"页面演示"与"批量评测"行为一致
- 每次运行输出完整 `trace`（步骤、工具调用、中间结果、token 用量），既是前端展示数据源，也是提交材料中的"代表性运行记录"

## 3. 用户故事（Web 交互）

- **U1 单轮直达**：输入 "Find a shirt about Barn from Konopelski-Inc with price under $17" → 页面展示推理时间线（解析→检索→比较→决策）→ 展示选中商品卡片与解释
- **U2 追问补全**：输入模糊需求 → Agent 追问预算 → 用户补充 → 决策更新（页面约束状态可视化变化）
- **U3 中途改条件**：已有推荐后说"太贵了" → Agent 在原约束上追加价格上限重新检索 → 新推荐
- **U4 零结果处理**：提出不可能满足的组合 → Agent 诊断冲突来源 → 给出放宽选项按钮 → 用户选择后重新检索

## 4. 非功能需求

| 编号 | 需求 | 目标 |
|---|---|---|
| N1 | Token 消耗 | 两阶段检索 + 候选截断；单轮对话 ≤ 2 次 LLM 调用（解析 1 次、比较+决策+解释合并 1 次）；每轮记录 input/output tokens |
| N2 | 响应延迟 | 流式输出（SSE）缓解等待；检索层毫秒级 |
| N3 | 可观测 | 每次运行落盘完整 trace（JSONL），含每步耗时与 token |
| N4 | 可复现 | requirements.txt + README 运行说明 + .env 模板（.env.example，不含真 key） |
| N5 | 安全 | API key 仅存 .env，不进代码不进仓库 |

---

## 5. 验收标准（无官方指标 → 自建量化指标）

1. **格式兼容**：50/50 任务通过 `simulate_agent.py` 输出结构校验
2. **决策质量**：编写自动评估脚本，从任务文本程序化解析出期望约束，校验 `purchased_product_id` 是否满足全部硬约束 → 输出**硬约束满足率**（这是核心质量指标）
3. **交互完整**：Web 端完整演示 U1–U4 四个场景（含 ≥3 轮对话）
4. **优化可量化**：输出 token 对比报告——基线（全量商品入 prompt）vs 优化方案（两阶段检索），覆盖单轮均值与 50 任务总量

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| LLM 解析约束输出格式不稳定 | 强制 JSON 输出 + 解析失败重试（最多 2 次）+ 兜底默认值 |
| API 网络波动 | 统一封装调用层：超时、重试、异常降级（检索结果直接透传，标记降级） |
| 多轮状态膨胀 | 服务端只存结构化约束状态 + 精简历史，不无限累积原始对话 |
| 任务文本解析歧义（评估脚本） | 评估脚本用规则解析任务句式（3 种固定句式），无法解析的样本人工标注 |
