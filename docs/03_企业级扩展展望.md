# 03 企业级扩展展望：原型到大厂生产级要换什么

> 核心结论：**Agent 的"想→做→看"循环、两阶段检索、硬/软约束体系、trace 可观测
> 这些架构思想不随规模改变；需要更换的是承载它们的基础设施。**
> 本原型每一层都刻意选择了"最小够用"的实现，且层间接口清晰，升级路径如下。

## 1. 检索层（变化最大）

| | 本原型 | 生产级 |
|---|---|---|
| 规模 | 96 条商品，内存 dict | 亿级商品（淘宝量级 ~10 亿） |
| 引擎 | 纯 Python 结构化过滤 | 分布式搜索引擎（Elasticsearch / 自研倒排索引） |
| 语义检索 | 不做（描述是占位文本） | 真实商品有图文详情 → 向量库（Milvus/FAISS）+ BM25 混合检索，即 RAG 架构 |
| 升级触发条件 | — | 商品量 > 内存可承载，或出现"模糊语义需求"（"送女朋友的、温馨一点的"） |

本原型的检索层已抽象为 `ProductStore.search()` 单一接口，换 ES/向量库只替换一个模块——这就是技术选型文档里"留好升级口"的兑现。

## 2. 状态层

| | 本原型 | 生产级 |
|---|---|---|
| 会话状态 | 进程内存 dict，重启即失 | Redis（热会话，带 TTL）+ MySQL/PostgreSQL（对话历史、订单、用户画像持久化） |
| 多实例 | 单进程 | 服务无状态化，会话外置后任意实例可接管任意会话 |

关键设计延续：**"结构化约束状态 + 滑动窗口历史"的记忆双层结构**在分布式下同样成立——约束状态存 Redis，历史消息落库。

## 3. 模型层

| | 本原型 | 生产级 |
|---|---|---|
| 模型 | 单一 deepseek-v4-pro | **模型路由**：简单请求走便宜模型（如 v4-flash，价格约 1/3），复杂决策走 pro；主模型故障自动降级备模型 |
| 密钥 | .env 文件 | KMS 密钥管理服务，权限最小化 |
| 成本 | 不控制 | 配额/预算系统、按业务线成本分摊，缓存命中率与 token 看板 |
| 评估 | 50 条公开任务 + 自建指标 | 固定评测集回归 + 线上抽检 + LLM-as-judge 自动打分 |

"会话级思考开关"（本项目实测踩坑后的设计）在生产里演化为按请求复杂度动态决策。

## 4. 服务层

| | 本原型 | 生产级 |
|---|---|---|
| 部署 | 单进程 `python -m app.api.server` | 容器化（Docker/K8s）+ 负载均衡 + 自动扩缩容 |
| 流式 | SSE 单向推送 | SSE 够用则保留；需要"用户中途打断生成"则升级 WebSocket |
| 削峰 | 无 | 推理请求进消息队列（Kafka）排队，避免突发流量击穿模型配额 |
| 缓存 | 依赖模型侧前缀缓存 | 业务侧语义缓存：相似问题直接返回缓存结论，省掉整个 Agent 循环 |

## 5. 可观测与质量（大厂真正的重点）

- **全链路追踪**：本原型的 `trace` 是手写版；生产接 OpenTelemetry，一次对话的每次模型调用、工具执行、耗时、token 全链路可查
- **指标告警**：延迟 P99、工具成功率、决策质量抽样、token 成本异动告警
- **安全护栏**：输入侧防提示词注入，输出侧合规审核；本原型的"护栏校验（决策违反硬约束自动纠正）"是其雏形
- **真实交易闭环**：购买决策要接库存/订单系统——库存预占、幂等、对账、回滚，进入事务领域

## 6. 前端

单文件 HTML/JS → React/Vue + 工程化构建。注意判断标准的变化：原型期"零构建链"是优点（评审一键运行）；团队协作期"组件化、类型检查、测试覆盖"才是优点。**技术选型的标准随团队规模和生命周期变化**，这本身就是选型方法论的一部分。

## 7. 什么不变（架构思想的迁移性）

以下设计在亿级商品的真实导购系统里依然成立，也是本作业最想展示的部分：

1. Agent 工具循环："抽约束 → 检索 → 观察 → 决策/追问"的职责划分；
2. **确定性检索先行、LLM 只做最后比较决策**——不让模型大海捞针，既省 token 又保准确率（业界主流实践）；
3. 硬约束/软偏好分离的约束体系与逐约束证据；
4. 零结果诊断（瓶颈定位 + 放宽建议）驱动的主动追问；
5. 决策留痕（trace）与违反约束的自动纠正。
