# 实验报告：购物 Agent 原型系统

> **任务 1：Agent 工作流构建**
> 仓库地址：https://github.com/tourist171514/shopping-recommendation-agent
> 模型：DeepSeek V4 Pro（官方 API，OpenAI 兼容端点）
> 数据集：[stockholmux/ecommerce-sample-set](https://github.com/stockholmux/ecommerce-sample-set)（CC BY-SA 3.0），
> 材料包为其中 96 商品 / 50 任务的种子抽样（seed=20260705），本报告另含 **1740 商品全集**验证

---

## 1. 项目概述

本项目构建了一个**可运行的购物 Agent Web 原型系统**：用户以自然语言提出购物需求，Agent 自主规划步骤、调用工具检索商品、观察结果、检查约束，最终给出购买决策与解释；支持多轮对话与主动追问。

题目要求的主干功能与实现对照：

| 题目要求 | 实现方式 |
|---|---|
| 需求理解 | LLM 从自然语言抽取结构化约束，区分硬约束与软偏好 |
| 商品搜索 | 两阶段检索：代码结构化过滤（0 token）→ Top-K 候选 |
| 候选比较 | 仅 Top-5 候选进入 LLM 上下文，附带逐约束匹配证据 |
| 约束检查 | 硬约束逐条校验 + 违反证据；软偏好计分不淘汰 |
| 购买决策 | 唯一商品或明确拒绝；护栏自动纠正违约决策 |
| 结果说明 | 自然语言解释"为什么选/没选"，每个约束的作用 |
| 拓展：多轮对话 | 会话级累积约束状态 + 滑动窗口历史 |
| 拓展：主动追问 | 零结果诊断驱动的追问 + 可点击放宽选项 |

**快速运行**：

```bash
pip install -r requirements.txt
cp .env.example .env        # 填入 DeepSeek API key
python -m app.api.server    # 打开 http://127.0.0.1:8000
```

## 2. 需求与数据勘察

动手前对数据做了实际勘察，三个发现直接决定了架构（详见仓库 `docs/01_需求分析.md`）：

1. **商品库极小（96 条、2 品类）且 `description` 全部是拉丁占位文本**
   → 不做向量/语义检索，结构化过滤 + 关键词匹配即最优；语义理解力用在"理解用户指令"而非"搜商品"。
2. **50 条任务分 3 种固定句式，含软偏好表述**（"prefer X if available"、"affordable"）
   → 约束体系必须区分硬约束（不满足即淘汰）与软偏好（只加分）；"affordable" 不得折算为杜撰的价格上限。
3. **题目无官方评测指标**
   → 自建量化指标：硬约束满足率、格式校验通过率、单任务 token/延迟、与"全量商品入 prompt"基线的对比。

## 3. 技术选型与论证

完整论证见仓库 `docs/02_技术选型.md`，此处给出结论与关键取舍。

### 3.1 选型结论

| 决策点 | 选择 | 依据 |
|---|---|---|
| 模型接入 | openai SDK + DeepSeek 兼容端点 | 实测支持函数调用；前缀缓存自动生效 |
| Agent 编排 | **自研函数调用工具循环**（约 300 行） | 题目原文要求"自主规划、调用工具、观察结果"，即工具循环定义；自研可完全控制提示词、trace 与 token 记账 |
| 检索 | 内存结构化索引（类型/厂商/标签/价格） | 数据勘察结论；接口抽象，可无缝升级 SQLite/ES |
| 后端 | FastAPI + SSE | 已装依赖最少；trace 以事件流推送 |
| 前端 | 原生 HTML/CSS/JS（零构建） | 评审者 `pip install` 后一条命令跑通 |

### 3.2 为什么不用主流框架（取舍说明）

- **LangChain / LangGraph**：核心循环本身仅数百行，框架会隐藏本题恰恰要考察的工具设计与编排逻辑，且引入版本耦合；复杂流程图编排在本场景（2 工具单主线）无收益。
- **CrewAI 等多智能体框架**：单导购即可完成的任务引入多角色只会倍增延迟与 token，无质量收益。
- **RAG / 向量检索**：语料无语义（占位文本）、查询为结构化硬条件，"按语义相似度找"反而把确定性问题做成不确定问题。**升级触发条件已写明**：商品规模超出内存，或出现真实图文描述与模糊语义需求时启用（全集验证见 §8，描述仍为占位文本，结论在 18 倍规模下依然成立）。

### 3.3 模型能力实测（选型前置验证，非纸面推断）

| 验证项 | 结果 | 影响 |
|---|---|---|
| 函数调用 | ✅ 正确抽取参数调用工具 | 采用工具循环 |
| 思考开关 | ✅ 可关：同一问题 202→44 tokens、3.4s→1.9s | 成本杠杆 |
| **思考开关隐藏约束** | ❌ 同一会话内切换开关 → 400 错误 | 降级为会话级开关（§6.2） |
| 前缀缓存 | ✅ 自动生效 | 多轮低成本 |

## 4. 系统架构与工作流设计

### 4.1 总体架构

```
┌──────────── Web 前端（原生 JS，SSE 消费）────────────┐
│  对话流 / 推理时间线 / 商品卡片 / 约束面板 / 追问选项按钮  │
└────────────────────────┬───────────────────────────┘
                         │ POST /api/chat (SSE)
┌────────────────────────▼───────────────────────────┐
│  FastAPI 层：会话仓库(内存) + 事件流转发               │
├────────────────────────────────────────────────────┤
│  Agent 核心（工具循环）                                │
│  ┌──────────┐   ┌──────────────┐   ┌────────────┐  │
│  │ 提示词协议 │   │ 工具执行器     │   │ 会话状态    │  │
│  │ (prompts) │   │ search/detail │   │ 累积约束    │  │
│  └──────────┘   └──────┬───────┘   └────────────┘  │
│                        │                            │
│  ┌─────────────────────▼─────────────────────────┐  │
│  │ 检索层（纯代码 0 token）：过滤→打分→证据→诊断      │  │
│  └─────────────────────┬─────────────────────────┘  │
│                        │                            │
│                 products.jsonl（96 条）              │
└────────────────────────────────────────────────────┘
```

### 4.2 Agent 工具循环（"真 Agent"而非固定流水线）

```
用户输入 + 会话状态行 + 历史
   ↓
LLM 调用①：自主决定调用 search_products（约束抽取内化于此）
   ↓ 工具执行（纯代码）：返回 Top-5 候选 + 逐约束证据 + 零结果诊断
LLM 调用②：观察结果 → 输出自然语言答复 + <decision> 结构化决策块
   ↓（特殊情况可再循环，硬上限 5 次防失控）
解析决策 → 护栏校验 → 更新会话状态 → 推送前端
```

- **下一步做什么由模型根据上一步观察结果自主决定**：零结果时自主放宽重搜或追问，指代追问时自主调 `get_product_detail`——固定流水线做不到这些。
- **正常路径恰好 2 次 LLM 调用**（50 任务实测 100% 两轮收敛，见 §8.1）。
- 可靠性三件套：**决策解析失败自动修复重试**（补发 `<decision>` 块）；**护栏校验**（选购商品违反硬约束时自动替换为最优合法候选并留审计记录）；**循环上限降级**（超限移除工具强制作答）。

### 4.3 两阶段检索（检索流程优化核心）

1. **代码过滤（0 token）**：类型 → 价格 → 厂商 → 标签（多标签 OR 命中），毫秒级；
2. **打分排序**：标签命中 +2/个、硬厂商匹配 +3、软偏好命中 +2；确定性排序（分→价→ID）；
3. **逐约束证据**：每个候选携带"哪个约束满足/未满足/为何加分"，直接支撑约束检查与前端展示；
4. **零结果诊断**（主动追问的弹药）：逐步收敛链（48→1→0 式展示卡在哪）+ 逐约束放宽（leave-one-out 指出放宽哪个能救回多少）+ 最近可行价（"最便宜的也要 $10.99，可提高预算"）。

### 4.4 多轮对话与主动追问（拓展功能）

- **累积约束状态**：新一轮只覆盖提到的约束键，未提及的保留；显式清空（"不要厂商限制了"→ 键置空即删）；
- **记忆双层结构**：结构化约束（永不截断）+ 对话历史（滑动窗口 20 条，截断安全）；
- **追问三触发**：零结果（诊断 + 可点击放宽选项）、信息不足、模糊表述；
- **追问策略**：有候选必给当前最优推荐（可顺带追问），零候选才必须追问——不做"只会提问的问卷机器"；
- **"太贵了/便宜一点"无数字时**：主动把预算降至上轮最低候选价的 80% 重搜，搜不到再给放宽选项（追问前先行动）。

## 5. 提示词与工具设计

### 5.1 工具集（最小化，2 个）

```jsonc
search_products(item_type?, tags?, manufacturer?, max_price?, prefer_manufacturer?)
// → 候选列表(含匹配证据) 或 零结果诊断
get_product_detail(product_id)
// → 单商品详情（支撑"第二个看看"式指代）
```

工具描述中直接写入约束语义（"用户未明确预算时不要编造"、"prefer X if available 填 prefer_manufacturer 不作硬过滤"），把领域规则前置到模型决策点。

### 5.2 系统提示词要点（`app/agent/prompts.py`）

- 工作流"抽约束 → 检索 → 观察 → 决策/追问"写明但**不强制顺序**，由模型自主执行；
- 硬/软约束区分规则、模糊表述处理规则、多轮增量规则逐条列出；
- **输出协议**：自然语言答复 + 结尾唯一 `<decision>{...}</decision>` JSON 块（`action / purchased_product_id / constraints_update / follow_up_options`），兼顾可读回复与结构化决策、前端渲染与追问按钮；
- 约束：商品 ID 只能来自工具结果（防幻觉）、语言跟随用户、不透露内部细节。

### 5.3 提示词中的反幻觉设计

候选序列化（`Candidate.to_llm_dict`）**刻意剔除无语义的 description**、只给结构化字段与证据；工具返回附带"ID 必须来自检索结果"的提示——从数据供给端压缩幻觉空间，同时节省 token。

## 6. 大模型使用方式

### 6.1 接入与成本控制

- DeepSeek V4 Pro 官方 API（OpenAI 兼容端点），封装层统一提供超时、重试、token 记账（区分输入/输出/思考/缓存命中/延迟）；
- **前缀缓存利用**：系统提示词 + 状态行作为稳定前缀，实测单任务缓存命中 2560/3035 = **84%**，多轮对话增量成本极低；
- 成本量级：50 任务总消耗 179,196 tokens（约 $0.1 量级）。

### 6.2 思考模式：从"按步骤开关"到"会话级开关"（踩坑与降级）

原设想"机械步骤关思考、决策步骤开思考"，对照实验发现 **DeepSeek 禁止同一会话中途切换思考模式**（关→开触发 400: `reasoning_content must be passed back`；开→开、关→关均可）。降级为会话级统一开关（默认开），关思考保留为对照组。思考模式的量化收益（同一问题）：

| 模式 | tokens | 延迟 |
|---|---|---|
| 开思考 | 241 | 3.9s |
| 关思考 | 53 | 1.9s |

思考开/关对最终决策质量的影响在 50 任务上均为 100% 正确（关思考组为抽查验证），说明本任务的约束抽取对思考不敏感；保留默认开思考是为覆盖更复杂的真实表述。

## 8. 结果分析

### 8.1 子集批量评测（50 个公开任务，全量）

评测方法：`eval/batch_run.py` 逐条调用 `Agent.run()`（兼容 starter 接口），`eval/auto_eval.py` 用规则解析任务期望约束后校验决策。关键设计：**先判可行性再判对错**——若任务本身无解，则"诚实不购买"也算正确，避免误伤。

| 指标 | 结果 |
|---|---|
| 输出格式校验（starter 标准） | **50/50 通过，0 错误** |
| 硬约束满足率 | **50/50 = 100%** |
| 软偏好命中（T3 句式） | 16/16 = 100% |
| 工具循环轮数 | 全部 2 轮收敛，无失控 |
| 平均消耗 | 3,584 tokens/任务（最小 3,171，最大 4,936） |
| 平均延迟 | 7.34s（含 2 次思考模式调用） |
| 本次运行总消耗 | 179,196 tokens |

### 8.2 全集验证（1740 商品，响应"找全集测会准一点"的建议）

从上游仓库拉取完整 `items.json`（1740 条，字段同源），无损转换为项目 schema，并按实测的 3 种句式模板合成 150 条任务（种子与材料包一致）。脚本：`eval/fullset_prepare.py` / `eval/fullset_eval.py`。

**A. 检索层（纯代码，150 任务）**

| 指标 | 子集（96 商品） | 全集（1740 商品，18 倍） |
|---|---|---|
| 检索延迟 | <1ms | avg 0.88ms / p95 **1.24ms** |
| 硬约束过滤后平均候选数 | ~4 | **4.3**（1740 → 4.3 的收敛能力不变） |

**B. Token 优化：与"全量商品入 prompt"基线的真实对比**

| 方案 | 单任务 prompt tokens（全集 1740 商品） |
|---|---|
| 基线：商品库整体塞入提示词 | **166,106**（实测） |
| 本项目：两阶段检索 | **~3,583**（30 任务端到端实测均值） |
| **节省** | **97.8%（约 1/46）** |

在 96 条子集上该差距仅约 2 倍——**这正是全集测试的价值：优化项的真实收益只有在规模放大后才显现**。

**C. LLM 端到端抽样（30 条全集任务走完整 Agent 循环）**

| 指标 | 结果 |
|---|---|
| 决策正确率 | **30/30 = 100%** |
| 平均消耗 | 3,583 tokens/任务 |

关键结论：**token 消耗与商品库规模无关**（子集 3,584 ≈ 全集 3,583），因为进入 LLM 的永远只是检索裁剪后的少量候选——两阶段架构的成本复杂度是 O(候选数) 而非 O(商品库)。

### 8.3 优化项汇总（对照题目"选取优化项突出思考与实践"）

| 编号 | 优化项 | 量化证据 |
|---|---|---|
| O1 | 两阶段检索（代码预裁剪，候选才进 LLM） | token 较基线省 97.8%；全集检索 p95 1.24ms |
| O2 | 结构化状态 + 滑动窗口历史 | 长会话成本有界；约束截断安全（状态双层） |
| O3 | 思考模式会话级开关 + 量化对照 | 关思考 token ↓78%、延迟 ↓51%（同题对照） |
| O4 | 缓存友好提示词工程 | 稳定前缀缓存命中 84%；候选剔除无意义描述 |
| O5 | 可靠性工程（修复重试/护栏/循环上限/重试） | 50 任务 0 格式错误、0 失控、违约决策自动纠正 |
| O6 | 零结果诊断驱动的主动追问 | 收敛链 + leave-one-out + 最近可行价（§7.3） |

## 9. 踩坑与解决（实践记录）

| 问题 | 定位方法 | 解决 |
|---|---|---|
| 第二轮调用稳定 400 | 设计三组对照实验（开→开/关→开/关→关） | 发现 DeepSeek 禁止会话内切换思考模式 → 会话级开关 |
| 多轮"失忆" | 复现用户场景，对比脚本测试与前端真实链路 | 前端 `conversation_id` 从未回传，每条消息都新建会话 → 从 `done` 事件捕获会话 ID |
| `.env.example` 无法入库 | `git check-ignore -v` 定位 | `.env.*` 误杀；加 `!.env.example`（并踩了 gitignore 不支持行内注释的坑） |
| Windows 控制台中文崩溃 | GBK 编码无法输出特定字符 | 全链路 `PYTHONIOENCODING=utf-8` + stdout reconfigure |
| 测试断言浮点误差 | `10.99 % 1 != 0.99` 假失败 | 改为验证真正的设计前提"不存在整数价格" |
| 批量评测进程中断 | 结果文件行数对账 | 增加 `--offset` 断点续跑 + 按 task_id 去重 |

## 10. 局限性与企业级扩展展望

**当前局限**：会话状态存内存（重启清空）；单进程部署；评测任务为模板化句式，对高度口语化/歧义表述的鲁棒性有待扩展集检验。

**扩展路径**（详见仓库 `docs/03_企业级扩展展望.md`）：检索层 → Elasticsearch/向量混合检索（亿级商品 + 真实图文描述时）；状态层 → Redis + 数据库；模型层 → 多模型路由与降级；服务层 → 容器化 + 队列削峰 + 语义缓存；观测 → OpenTelemetry 全链路。**不变的是**：工具循环、"确定性检索先行 + LLM 终局决策"、硬/软约束体系与决策留痕——这些架构思想不随规模改变。
