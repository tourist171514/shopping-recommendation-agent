# 02 技术选型

> 决策依据：`任务1_Agent工作流构建_题目.md` + `docs/01_需求分析.md`
> 每项选型均标注其对应的需求/题目出处，全部经过实际 API 验证（非纸面推断）。

## 0. 已验证的模型能力（选型前提）

| 验证项 | 结果 | 对选型的影响 |
|---|---|---|
| 函数调用（function calling） | ✅ 正确调用 `search_products` 并抽取参数 | 可采用工具循环编排（见 §2） |
| 思考模式开关 | ✅ `thinking.type=disabled` 有效：3.4s→1.9s，202→44 tokens | 思考可关，但见下方"会话内禁止切换"约束 |
| **思考开关的隐藏约束** | ❌ 首轮关思考、次轮开思考 → 400（`reasoning_content must be passed back`）；对照实验确认开→开、关→关均可 | "分步骤选择性开关"不可行，降级为**会话级统一开关**（见 §1） |
| 前缀缓存 | ✅ 自动生效（首轮即命中 256 tokens） | 多轮对话的 system prompt 几乎零增量成本 |
| 模型性质 | 推理模型（含 reasoning_tokens） | token 统计需区分思考/输出 |

## 1. 模型接入：OpenAI SDK + 官方兼容端点

- **方案**：`openai` Python SDK，`base_url=https://api.deepseek.com`，模型 `deepseek-v4-pro`
- **封装层 `app/llm.py`** 统一提供：超时（30s）、失败重试（2 次）、token 用量记账（区分思考/输出/缓存命中）、流式输出
- **思考开关（会话级）**：
  - 原设想"机械步骤关思考、决策步骤开思考"，实测发现 DeepSeek 禁止同一会话内
    切换思考模式（400 错误），故调整为会话级统一开关，默认开启保质量；
  - 关思考模式保留为批量评测的对照实验组（质量/成本量化对比，见 eval/）；
  - 对照需求 N1"单轮 ≤2 次 LLM 调用 + token 可控"
- **不选** LangChain 的 ChatModel 封装：多一层抽象、版本耦合重，而本项目只需 chat.completions 一个端点

## 2. Agent 编排：自研函数调用工具循环（不用 LangChain/Agent 框架）

**题目原文依据**："Agent 系统需要根据用户目标**自主规划步骤、调用工具、观察中间结果**并完成任务"——这正是工具循环（tool loop）的定义；固定流水线不符合"自主规划"。

**循环结构**：
```
用户输入 + 会话历史 + 工具定义
   ↓
LLM 调用① → 决定调用 search_products(结构化约束)   [约束抽取内化在这一步]
   ↓ 执行检索（纯代码，0 token），返回 Top-K + 匹配明细 + 无匹配诊断
LLM 调用② → 观察检索结果 → 输出最终答案：
   比较 + 购买决策 + 解释（或：主动追问 / 放宽建议）
   ↓（特殊情况如需要追加检索，允许再循环，设 5 次上限防失控）
```

- **正常路径恰好 2 次 LLM 调用**，满足需求 N1；多轮追问场景由会话历史自然承载
- **工具集**（最小化，2 个）：
  - `search_products(item_type?, tags?, manufacturer?, max_price?)` → Top-K 候选 + 每个约束的满足情况 + 空结果诊断
  - `get_product_detail(product_id)` → 单商品完整信息（用于"第二个看看"类指代追问）
- **不用框架的理由**（写入实验报告）：工具循环本身仅 ~100 行，自研可完全控制提示词、trace 结构与 token 记账；框架反而掩盖题目要考察的设计能力
- **对照需求**：F1–F6 主干功能映射到两次调用；F7 多轮（会话状态）、F8 追问（空结果诊断 + 模糊表述由 LLM 在答案中发起）

## 3. 检索方案：内存结构化索引（无向量库、无数据库）

**需求依据**：勘察结论——96 条商品、description 为占位文本、检索键是结构化字段。

- 启动时加载 `products.jsonl`，构建四个索引：`按类型`、`按厂商`、`标签倒排`、`价格排序表`
- 检索 = 索引交集过滤 + 匹配打分（标签命中数、厂商精确匹配、价格余量）
- 返回结果附带**逐约束满足证据**（哪个约束过/没过），直接支撑 F4 约束检查与 F8 零结果诊断
- **可升级性**：检索层抽象为接口，若用全集（数千商品）验证，可无缝换成 SQLite，上层不变（对应学长"找全集测"的建议）
- **明确不做**：向量检索（语料无语义）、独立数据库（规模不需要）——在报告中说明"为什么不做"与"什么时候该做"，体现取舍判断

## 4. 后端：FastAPI + SSE 流式

- **方案**：FastAPI（本机已装 0.115.6）+ `StreamingResponse` 实现 SSE
- **接口设计**：
  - `POST /api/chat`（SSE）：入参 `{conversation_id?, message}`，流式推送：`trace 事件`（每步工具调用与观察）→ `delta 事件`（答案流式文本）→ `done 事件`（结构化决策结果）
  - `GET /api/session/{id}`：当前会话的累积约束状态（前端可视化"约束面板"）
  - `POST /api/session`：新建会话
- **会话状态**：内存 dict `{conversation_id: {constraints, history, candidates, decision}}`（需求 N3；原型阶段不落库，重启清空可接受）
- **对照需求**：N2 流式缓解延迟；trace 事件流 = U1–U4 页面展示数据源 = 提交材料的运行记录

## 5. 前端：原生 HTML + CSS + JS（零构建工具链）

- **需求依据**：N4 可复现（评审者 `pip install + python -m app.api.server` 即可运行，不需要 Node 环境）
- FastAPI `StaticFiles` 直接托管，前后端同一进程，部署最简
- 页面结构：
  - 对话区（聊天流，含 Agent 追问气泡与可点击的放宽选项按钮）
  - **推理时间线**（trace 可视化：解析→检索→观察→决策，每步展示工具入参/出参摘要与 token）
  - 商品卡片候选区（展示匹配/违反的约束徽章）
  - 约束状态面板（多轮累积约束的实时可视化，支撑 U2/U3 演示）

## 6. 兼容性设计（对接官方评测骨架）

- `app/agent/core.py` 中的 `Agent` 类同时提供：
  - `run(instruction) -> dict`：完全兼容 `starter/agent_interface.py` 约定，`simulate_agent.py` 零修改可跑
  - `chat(conversation_id, message)`：Web 多轮入口
- 两个入口共享同一工具循环与检索层，保证"页面演示效果 = 批量评测行为"

## 8. 选型风险备注

| 风险 | 缓解 |
|---|---|
| 推理模型延迟较高 | 机械步骤关思考 + SSE 流式 + 前缀缓存 |
| 工具循环失控（反复调用） | 硬上限 5 次循环，超限降级为基于已有结果作答 |
| LLM 输出 JSON 格式偶发损坏 | 解析失败重试 2 次，再失败降级为纯文本兜底 |
